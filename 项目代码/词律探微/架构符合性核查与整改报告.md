## 3. 专项判定："是否真正实现了不靠堆砌字段来实现问答？"

**机制层面：是。** 三条硬证据：

1. **字段清单只有一份**：`queryplan.LEAF_SCHEMA` 是唯一真源，Planner 提示词、校验器、编译白名单全部由它派生；`check_schema_alignment()` 双向对齐自测**全绿**（26 字段）——从机制上杜绝了"再加一个字段就要改三处"。
2. **新增问法 = 组合算子，而非新增分支**：`plan_exec` 提供 `filter / sort / limit / group_by / aggregate / argmax / count / extract / pair / locate / intersect / union / diff / anchor / annotate / materialize_as` 16 个算子；`to_plan/from_plan` 双向无损。
3. **同义改写走数据表**：数值同义词已表化为 `NUM_SYNONYM_TABLE`（"加一种说法＝表里加一行"），实体识别已收口为 `entity_resolve`（"加一类实体＝改一处声明"）。

**运行层面：尚未完全生效。** 三条缺口：

1. **默认不启用**：`LVC_PLANNER=rule` → 组合式机制在默认下不参与执行。
2. **算子集不全**：缺 `median / mode / stddev / rank / join / similar_to / project` 等（审查 Top8/#10 明确要求）。
3. **旧分支仍在**：`ask.py` 的 `_answer_output/_answer_agg/_answer_pair`、`_absorb_*`、`rescue_title` 尚未迁为算子。

**判定：机制已达成（约占 70%），运行态未切换（约占 30%）。**

## 7. 本轮新发现的缺陷（必须修）

1. **`queryplan.to_spec` 不存在却被调用**：`qlm.understand()` 的 planner 分支 `spec = queryplan.to_spec(pl, conn)` → 必然 `AttributeError` → 被 `except` 吞掉 → **`LVC_PLANNER=planner` 永远回落填槽路**。（全仓 grep 无 `def to_spec`）
