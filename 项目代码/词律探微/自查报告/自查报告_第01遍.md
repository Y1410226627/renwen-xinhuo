## 二、本遍**新发现并已修**的问题

### 【自查-1-①・中】前端 `isHttpUrl` 比后端 `safe_url` 更宽 —— 协议相对/相对路径被当成链接

- 位置：`frontend/src/views/ResearchView.vue` 的 `isHttpUrl()`。
- 原实现：
  ```js
  const p = new URL(String(u), window.location.href);   // ⚠ 带 base
  return p.protocol === 'http:' || p.protocol === 'https:';
  ```
- **实测**（Node 22 复现，base = `https://example.com/page`）：

  | 输入 | 旧实现 | 后端 `safe_url` | 期望 |
  | --- | --- | --- | --- |
  | `//evil.com`（协议相对） | **OK（渲染成链接）** | BLOCK | BLOCK |
  | `foo/bar`（相对路径） | **OK** | BLOCK | BLOCK |
  | `\\evil.com`（反斜杠） | **OK** | BLOCK | BLOCK |
  | `javascript:alert(1)` | BLOCK | BLOCK | BLOCK |

- **危害**：前后端「同一道闸」口径不一致。后端写入侧挡得住的怪值，在前端（如历史数据 / SSR 注入路径）却被渲染成可点链接，指向当前站点下的相对地址——虽非 XSS，但属**误导性链接**，且违反「三处同一口径」的自我承诺。
- **修法**：前端只看**前缀**，不解析 base：
  ```js
  return /^https?:\/\//i.test(String(u).trim());
  ```
- **复测**：修复后 `//evil.com`、`foo/bar`、`\\evil.com` 全部 BLOCK，`https://ok.com`、`HTTP://OK.com`、`   https://ok.com` 全部 OK —— 与后端 `safe_url` 逐例一致。

## 三、本遍**已确认无问题**的点（正面结论）

- `safe_url` 的伪协议拦截面实测（用 `urlparse` 逐例跑）：
  `javascript:` / `JavaScript:` / ` javascript:` / `java\tscript:` / `java\nscript:` /
  `jav\x00ascript:`（scheme 为空 → 拒）/ `data:` / `vbscript:` / `x:javascript:` /
  `//evil.com`（无 scheme → 拒）/ `\x00javascript:` —— **全部 BLOCK**，无一绕过。
  （`urlparse` 自动小写化并剥控制字符，故无需自建规整。）
- `_row(cur, r)` 回落路径：`dict(r)` 失败时按 `cur.description` 拼列名，与 `Row` 路径同构。
- `_migrate` 二修正确：`cols = [r[1] for r in cur]`（`r[0]` 是 cid）。
- `run_idempotent`：`isinstance(row, sqlite3.Row)` 双路取值，外部连接不炸。
- `get_idempotent`：已改 `_row`，不再假定 `row_factory`。
- `add_text_version`：`ts = _now()` 一次取准，INSERT 与返回体共用。
