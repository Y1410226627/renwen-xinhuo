## 〇、一句话与一句口令

**一句话**：把清代词作的声律（逐字平仄 → 句级配置 → 篇级比例 → 声情转向）做成**可复算**的数字，
再让检索把**证据与原文**端上来，最后让大模型只负责「说得通顺」——每一处数字都要能被引擎追认。

**一句口令**：**数字归引擎、文料归检索、说法归生成、出处归引用。**

## 四、口径与规则（全部有实测依据，改一处必先跑回归）

- **切句**：句末标点 = 「。」「？」「！」（曲文亦按「？！」收句），标点保留在前句；统计只数汉字。
- **前段/后段**：前段 = 前 ⌊句数÷2⌋ 句，后段 = 其余。
- **进位口径（官方不一致，必须分别对待）**：C2「变化值」用**未舍入的原始比例相减**；
  C1 比例差／C2 变幅／C3 密度／C4 比例差用「各自保留一位再相减」。
- **舍入**：**银行家舍入**（`ROUND_HALF_EVEN`），不是四舍五入。
- **汉字判定**：`[\u3400-\u4dbf\u4e00-\u9fff]`（CJK 统一表意 + 扩展 A）；`□ ○ ■` 等占位符不算。
- **标定表**：仅 3 字（长 cháng／别 biè／绝→仄），每条都带 `basis` 与净增益说明；零破坏是硬门槛。
- **定位**：三重匹配（作者＋词牌＋首句），低置信路径写进 `errors`；同分优先 poetry-source。
- **句脚字**：该句**最后一个汉字**（跳过占位符与标点）。
- **引文**：一律原样（含标点），不得补标点或改字。

## 五、护栏与检索（为什么数字不会造假）

- **检索五路**：FTS5 二字组（BM25）／短语／元数据（朝代·词人·词牌）／数值条件／声律模式与声情，融合排序取 top-k。
- **证据块**：每块带 `pid`（可点回原文）、引擎算出的数字、句级原文。
- **四道护栏**：① 数字必须来自被引证据块的字段；② 引文必须逐字且为整句；③ 无据即认账（拒答不许带数字与引文）；④ 边界声明与问句类型匹配。
- **内容安全**：入向（提问）命中即不进检索；出向（大模型叙述）命中即整段丢弃。

## 六、大模型怎么用（第十四轮起）

**默认不调用任何模型**；只有显式启用（`--llm` / `--argument` / 网页勾选框）时才走「说法层」：
大模型拿到的是**事实清单**（不是语料全文），写完后**整段再跑一遍护栏与内容安全**，不过就丢弃、回落模板。
所以**接不接大模型，答案里的数字一模一样**；接上只是话更顺、并多出一段「论证表述／论证辅助草稿」。

### 19.5 三条教训

1. **自检的「通过」要分强弱**：一次把所有字段都改错，只要报出任意一个就算过——那基本没测。
   要**逐字段**制造变异，才逼得出「哪个字段根本没人管」。
2. **文档写的口径必须与代码一致**：我在 §十五 写「排序改严格次序相等」，代码里却一直是集合口径；
   写下来的承诺要能被一条命令验伪，否则就是自欺。
3. **外部交付的自检输出同样要核对**：对方把「分阕分组差异」读成「标点差异」，差点让我以为多出一组跨源重文。

### 20.3 本轮自检（新角度：**对照本身也会放空炮**）

**★ 真问题（本轮最值得记的一条）**：我的跨实现对照脚本第一次跑，`sqlite3` 的
`description` 取了下标 `[1]`（那是**类型码**，全是 `None`）而不是 `[0]`（列名）。
结果：字段名一个都没对上 → **一条字段都没比**，脚本却打印「✓ 全部一致」。

- 「**没比**」和「**比了且都一致**」在输出上长得一模一样——这是最危险的一类自检假通过。
- 修法：① 按语义对齐列名（`han_len↔n_char`、`sent_n↔n_line`、`ping↔n_ping`、`ze↔n_ze`）；
  ② 加护栏「**比对项数为 0 即 FAIL**」；③ 打印实际比对项数（修好后为 **3,000 项**）。
- 同类加固（防同类漏洞）：
  - `tools/eval_mutation.py`：变异数为 0 → 直接 FAIL（不许报「0 漏报」）。
  - `tools/regress.py`：新增全局检查计数，并在第九段自证「本段确实执行了比对」。
- 另做「文档 ↔ 行为」一致性抽检：我方 README 里的 **13 条命令逐条跑 `--help`/试跑**，全部为活（无过时参数）。

**新增第九段门禁**（交付产物一致性）：`corpus.db` 篇数 == 语料载入篇数（58,852）、句数合理、
校订队列非空且**只**集中在已知口径例外字。→ 门禁 **九段 23 项全过**。

### 21.3 本轮查出的真问题（都是「静默算错」型，不是崩溃型）

1. **句脚字口径错**（`tail`）。旧实现取「去掉句末标点后的末字符」→ 全库 **2,583 处**句脚字是

2. **前端映射漏了标定表**。`Pronouncer()` 不传参就**不带标定表**，页面把「绝」当平声 →
   同一首词页面上平 59、引擎平 58。改为显式传 `default_overrides_path()`，并加**启动断言**：

3. **映射两串错位**。护栏原来把「期望值」写成 `str(字典)` 拼进 `tones`，导致 chars/tones
   两串长度差 **708**，JS 侧整串错位、全部按「平」算。教训与第十一轮同源：
   **映射类产物必须校验「两串等长 + 逐键可取」**，不能只看「有没有报错」。
4. **`regress.py` 第九段指错文件名**（查 `data/reviews.csv`，实际产物是 `data/review_diff.csv`）
   → 段落长期处于「跳过」状态，**门禁空转而不自知**。已修，并把「跳过」与「PASS」在输出上分开。

### 21.4 本轮方法论（写给下一轮的我）

- **「没报错」不等于「算对了」**：三个真问题里有两个是**静默错值**（3 条里 2 条），
  唯一能抓住它们的办法是**另一套实现重算一遍**（JS vs Python），而不是再审读自己的代码。
- **跨实现对照要能报出「比了多少项」**：本轮对照若只打印「✓ 一致」，上面三个错都藏得住；
  正因为打印了 `比对 43,459 项，不符 0 处`，才一眼看出 `不符 26,024 处` 是崩了而不是「口径不同」。
- **门禁的「跳过」必须与「通过」分开写**：文件名写错 → 段落静默跳过 → 看起来全绿。
  已统一为：跳过必打印「（未生成：跳过 …）」且**不计入 PASS 计数**。
- **顺带学到的取舍**：外部交付的 `retrieve.py` 用手写倒排表（取 df/dl 要回查库，N+1 风险）、
  全文用 `LIKE`；我方直接用 **FTS5 内建 BM25**，并额外做了**它没有的「声律模式路」与「声情路」**——
  这两路才是这个榜题的题眼（声律/声情检索，不是普通全文检索）。

### 22.5 附：同一轮抓到的「句脚字」问法坑（静默答错型）

- 做网页示例问句时顺手一测，发现问「句脚是「愁」」被解析成 **句脚字=是** ——
  旧正则 `句(?:脚|末字|尾字)\\s*[=＝:：]?\\s*(汉字)` 允许分隔符缺省，于是把「是」吃成了句脚字。
  它会**正常召回、正常出证据块、护栏也通过** —— 也就是说：**答案是错的，但一切看起来都对**。
- 修法：允许 `是/为/作/等于` 与开引号，并新增「句脚平仄」能力（`句脚为平`/`句脚字是仄`）：
  `句(?:脚|末字|尾字)\\s*(?:字)?\\s*(?:[=＝:：]|是|为|作|等于)?\\s*[「『\\'"]?(汉字)`；
  捕获到 平/仄 时进 `tail_pz`，SQL 用 `substr(l.pz, -1, 1)`（**句脚平仄直接从 pz 串末位取，不用另存字段**）。
- 锁死：`selftest.py` 第 19 节 6 条断言（句脚=声 / 句脚是「愁」/ 句末字是愁 / 句尾字=雨 /
  句脚为平 / 句脚字是仄）；`tests/qa_cases.jsonl` 加 **Q023/Q024**（22 → **24 条**）。
- 教训（第四条同类）：**自检用例写得再全，也挡不住「问法」这一维**——
  用户不会按你的语法提问。凡是「解析用户输入」的地方，都要拿**口语变体**过一遍，
  而且必须检查「解析出的条件」而不是「有没有返回结果」（返回结果几乎永远有）。

## 二十三、2026-09-30 第十四轮：把「评分要点缺的三样」补进代码

### 23.1 为什么补（拿评分表逐条对照出来的缺口）

### 23.2 分工铁律（这一轮最重要的设计决定）

```
引擎 prosody/corpus   → 算数字
检索 retrieve/evidence → 取证据与原文
大模型 gen/llm        → 只负责把它写成通顺的话
护栏 guard/safety     → 逐行核对：数字有没有出处、引文是否逐字、有没有不当内容
```

- 大模型拿到的是**事实清单（FACTS）**，不是语料全文；提示词里明确「只能用 FACTS 里的数字」。
- 生成的正文拼上本类**边界声明**后，**整段再跑一遍 `guard.verify()`**（护栏①—④）＋ `safety.check()`。
- **任一不过 → 整段丢弃**，回答回落确定性模板，并在 `narrator` 里注明「已回退」。
- 因此：**接不接大模型，答案里的数字一模一样**；接上只是话更顺、并多出一段「论证表述」。
  这也是「数字归引擎、说法归大模型」这条口诀第一次真正落地成代码。

### 23.5 三条教训

1. **「技术上更好的做法」未必是「评分表要的做法」**——我们不接模型能拿满分，但评分要点第一条就要看大模型集成。

### 27.1 主人第四炮

诊断：问句被当成**普通检索**理解——只认出「朝代=宋」，其余整串

### 27.2 新增 `solve/aggregate.py`（M8 聚合统计层）

- `stats(conn, group_by, values, metric)`：在原库上 `GROUP BY` 统计——
  篇数 / 总字数 / 总仄字 / **篇均**（各篇指标的平均）/ **加权**（组内总量之比）。
- `compare(rows, metric)`：以**加权口径**（长词权重更大，更接近「整体」）定高下，
  同时核对篇均口径是否同意；**不同意就照实写「两种口径不一致」**。
- `render(...)`：确定性成文（组级数字 + 结论 + 口径说明），不含 markdown 强调符。
- 维度：朝代 / 词人 / 词牌；指标：仄声占比 / 平声占比 / 篇幅 / 句数。

### 27.3 解析（`retrieve.parse_agg`）

- 对比意图（哪个/哪一类/谁/对比/相比/统计/更高/更大…）+ **同维度 ≥2 个组** → 判为聚合题。

  普通题里「清」是**限定**，聚合题里「宋」「清」是**两个组**）；
  词人/词牌用库中名字匹配，并用 `_drop_sub` 去掉被更长名字包含的短名

### 27.7 教训

## 28. 第二十轮自检：前端「平/仄」列全 NaN（2026-09-30 晚，主人实测）

**症状（主人截图/贴回）**：在 `data/parse.html`（视图一·逐字解析）里点开纳兰性德《浣溪沙》
（`ci.清.0004.base.json#933`），篇级摘要一行完全正确
（`全篇 2 句 / 42 字：平 26、仄 16，仄声比例 38.1%；前段 33.3% → 后段 42.9%（变化 9.5），
声情 后段上升；最长句第 1、2 句；阈值 21`），但**表格最后一列「平/仄」显示 NaN**。

**根因（一行字符串减法）**：

```js
h+='<tr>…<td>'+L.pz.split('仄').length-1 +'/'+ L.pz.split('平').length-1+'</td></tr>';
```

JS 里 `+` 与 `-` **同优先级、从左到右** ⇒ 先做字符串拼接、再做减法：
`('<td>…' + 7) - 1` → 字符串减数字 → **NaN**。于是**每一行**的「平/仄」都是 `NaN`。
另外两处同批修正：**列序**（表头写「平/仄」，代码却按 仄/平 拼）与**单一来源**
（改用 `metrics.js` 已导出的 `Metrics.count()`，不再在模板里手搓 `split().length`）。

**为什么此前的门禁全都漏掉了它**（最该记的一条）：

| 门禁 | 比的是什么 | 为什么漏 |
| --- | --- | --- |
| `web/verify_views.js` | 前端 JS **算出的指标** vs Python 引擎（43,459 项） | 它比的是 `metrics.js` 的计算结果，**没跑页面拼 HTML 的那段代码** |
| `tools/views_check.py` 类检查 | 页面里**有没有**某关键字、某 pid | 只看「有没有」，不看「对不对」 |
| `solve/selftest.py` | 引擎内部断言 | 完全不涉及浏览器侧渲染 |

⇒ **教训：门禁要覆盖「渲染结果」，不能只覆盖「数据」。**
「页面自己拼出来的字符串」是第三个可独立出错的环节（引擎算对、数据传对、**拼错**）。

**新增常设门禁 `web/test_render.js`**（node，零依赖）：

1. 把 `data/parse.html` 的**内联脚本真的跑起来**（`vm` + `document` 桩）；
2. **逐篇**驱动 `draw()`，检查渲染出的 HTML：
   ① 不得出现 `NaN/undefined/Infinity`；② 表格行数 = 句数+1；
   ③ 每句「逐字平仄串」与页面自己的 `pzOf()` 一致；④ 每句「平/仄」计数与 `Metrics.count()` 一致
   （含**列序**）；⑤ 篇级摘要与 `Metrics.compute()` 独立复算一致；
3. **比对项数为 0 即 FAIL**（防「空跑报通过」）；
4. `--selftest`：把**旧的 NaN 写法注回页面**再跑一遍，**必须报错**——

## 31. 极值／排序题（「哪一首…最高/最低」）—— 第七炮整改（2026-09-30 深夜）

**主人实测（`D:\桌面\运行记录.txt`）**：问「高旭写的哪首词里仄声字占比最高」，
系统答「在条件〔词人=高旭〕下共命中 147 篇；**排序最前者**为 清·高旭《菩萨蛮》…仄声比例 38.6%」，
而 E2《昭君怨》是 42.5%、E3《卖花声》是 40.7%——**把 38.6% 说成第一**；
成文层还照这个错答案写了一整段「高旭的词作呈现出仄声占比相对较高的**共性**」。

### 31.1 三条根因

| # | 根因 | 表现 |
| --- | --- | --- |
| ① | **极值意图没有字段**：`QuerySpec` 里根本没有「按某指标排序／取极值」，`search()` 一律按**五路融合分**排 | 「最高」被当普通词面条件，融合分第一的篇目被当成答案 |
| ② | **文案在无排序条件时硬写「排序最前者为…」** | 这是一句**断言**；没有排序条件时它就是**虚假陈述** |
| ③ | **成文层不知道这是极值题** | 模型拿到的事实清单里没有「问的是哪一首」，于是写成「共同特征」——答非所问 |

顺带暴露一个真缺陷：语料**标题自身带「」**的篇目（《蝶恋花·魏里钱尔斐先生向有四月《蝶恋花》「戏」字韵词…》）
会让引文护栏把标题里的「戏」判成「凭空引用」——护栏只认「整句」，而标题不是句子。

### 31.2 改法

- `QuerySpec` 新增 `order_by / order_col / order_dir / extreme / order_label / order_src`。
- `retrieve.parse_extreme()`：**指标词 × 极值词**两段都要命中才认（最高/最多/最大/最长 ↔ 最低/最少/最小/最短），
  指标→SQL 列走 `ORDER_COLS` 白名单（平声比例是反向指标，自动翻向）；**认不出指标就不认这题，绝不猜**。
  摘下指标词与极值词后用同一套解析器解剩下的条件，并关掉「整串无分隔符就当正文片段」的兵险逻辑——
  否则「高旭」会被静默撤掉（实测：旧版把它整个变成词面条件 `词面=高旭写的、词里仄声字占比最高`）。
- `retrieve.search()`：排序题**直接按指标 SQL 排序**，与融合分无关。
- `retrieve.extreme_info()`：**独立 SQL 复算**极值、并列篇数、比较范围 —— 答案里写
  【极值复核】行（「引擎算出来的就是答案」也要能被第二条路径复算）。
- `ask.answer()`：极值题的结论行改写为「其中【仄声比例】**最高**的是 …」；
  **没有排序条件的题一律改说「融合排序最前者（本问没有指定排序指标）」**，不再含糊其辞。
  并列篇数超出展示篇数时，不许再写「已一并列入」，改说「此处展示前 N 篇」。
- `gen.facts()`：极值题往事实清单里加一行「【题型：极值题】本题问的是『哪一首…』，答案就是极值篇目，
  **不是**在找共同特征」——成文层据此对齐，不再写「共性」。
- 引文护栏：`「」` 允许两种落地方式——**等于某个整句**，或**逐字出现在标题/词牌/词人里**
  （语料标题自身带引号的情形）。句级「必须整句」的要求不变。
- 网页端：`/api/search` 排序白名单扩到 11 项（字数/句数/最长句/变化值的升降序），并在响应里给出 `sorts` 标签表；
  `/api/ask` 增加 `extreme` 字段（极值、并列、范围）。离线检索页的排序下拉同步。

3. **门禁的检测器必须自检**：`--selftest` 停掉解析器后必须报错，否则「门禁通过」毫无意义。

**主人第二次贴回 `运行记录.txt`**（这次是网页端、**勾了大模型理解**）：
```
【查询理解】（来源：大模型 zhipu:glm-4-flash）词人=高旭
　　　注：同一句用规则解析得到〔词人=高旭；排序=仄声比例（取最高）〕；本次执行以上表为准。
```

- `solve/selftest.py` §23 新增 4 项（大模型丢意图→规则补回 / 不得再说「已忽略——最高」/

### 32.4 教训（第三条是本轮最值钱的）

1. **「如实披露」不能替代「正确执行」**：注脚写着「规则解析得到排序条件」，正文却按没有排序执行——

2. **安全网要按「意图类型」逐个补齐**，不是修一个算一个：朝代、语料外朝代、对比题、排序——

   门禁也必须把「另一条路」当成一等公民来测。

## 33. 第八炮：配对题 + 网页四处实测整改（2026-09-30 深夜）

主人第三次贴回 `运行记录.txt`，这一问是**新的一类题**：
```
问：找出几对每个位置上的字平仄都相同的两首词
【查询理解】（来源：大模型 zhipu:glm-4-flash）声律模式=平仄平仄平仄平仄
　　　注：同一句用规则解析得到〔词面=找出几对每个位置上的字、都相同的两首词〕；本次执行以上表为准。
```
**两头都错**：规则路把整句当词面条件；大模型路更离谱——它从**问句本身**「捏」出一条
「声律模式=平仄平仄平仄平仄」（问句里根本没有这个谱），拿最严条件去筛篇，
返回 862 篇元曲残句，还按五路融合分排了个「最前者」。这题问的**根本不是「哪些篇满足某条件」，
而是「篇与篇之间的关系」**——配对。

### 33.1 新增 M8b：配对层（`solve/pairing.py`）

- `parse_pair()`：**三段都命中才认**——配对框架词（几对／两首／成对…）＋「相同」词＋**维度词**
  （平仄／声律／声调）。少一段就返回 None（**不猜**）。
- 判定量 = **全篇平仄串**（该篇每句 pz 按句序接起来）；两篇串逐位相同即为一对。
  串相同自然推出句数与字数相同——这一点写进了答案，不让读者自己推。
- `find_pairs()`：按串分组（`GROUP BY sig HAVING n>=2`），按「组内篇数 ↓、最小句数 ↓、谱长 ↓」取前几组，
  每组给**不同词人**的两篇（更有对照价值）；组数／对数／涉及篇数／分朝代数一并给出。
- `audit()`：**第二条独立路径**——Python 侧把每篇平仄串重算一遍再用 `Counter` 分组，
  并对展示的每一对做**逐位**比对（位位数／不同位数／首个不同位）。
- `parse_query()` 里把配对判定放在**最前**（早于极值题与普通条件题）；
  并且**不填** pz/keywords（这正是旧版翻车的地方）。

### 42.1 缺陷：问「题名」被判成问「词原文」（朋友实测驱动）
