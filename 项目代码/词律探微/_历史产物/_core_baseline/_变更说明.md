# _core_baseline 变更说明

本目录是 `frontend/tools/check-core.cjs` 的**冻结基准**（首次运行时自动拷贝 core 快照，之后幂等不覆盖）。
按项目约定：**凡修改 `frontend/src/core/*.js`，必须把改后的同名文件复制覆盖到本目录**，
否则「新 core ≠ 冻结基准」会让门禁 exit 1。本文件逐条记录本轮（2026-10-06 · 前端修复）的**有意行为修复**。

> 说明：本轮 4 处 core 改动只影响「边界/非法输入」路径。实测 `check-core.cjs` 在**同步基准之前**
> 也已是「比对项 213972 项，不符 0 项」——因为全库 26742 篇的 `splitSents / analyze.metrics /
> detailHtml` 与 12 条 SQL 标尺都不触发这些边界。同步基准是**按约定固化为「已批准的新语义」**，
> 使后续任何非预期漂移仍能被这道门禁抓到。

覆盖的文件：`metrics.js`、`parse.js`（`ui.js / review.js / ask.js` 未改动，保持原样）。

---

## 1. `metrics.js` — 空篇最长句字数 `-Infinity`（F1）

- **位置**：`compute(lines)` 内，原第 47–48 行 → 现第 47–51 行。
- **原行为**：`var mx = Math.max.apply(null, lens);`
  当 `lines` 为空数组（正文无汉字的空篇）时 `Math.max.apply(null, [])` 返回 `-Infinity`，
  经 `longest_len` 显示为 `-Infinity`。
- **新行为**：`var mx = lens.length ? Math.max.apply(null, lens) : 0;` → 空篇 `longest_len = 0`。
- **修复理由**：Python 端 `solve/prosody.py` 的 `longest()`（第 149–156 行）对空篇**显式返回
  最长句字数=0**。前端是「同一套口径的 JS 重算」，必须与引擎一致，不能出现 `-Infinity`。

## 2. `parse.js` — 数值条件 truthiness 判空（F2）

- **位置**：`matchCond()` 数值判定，原第 113–116、119 行 → 现第 123–132 行。
- **原行为**：`if (c.minLen && m.han_len < c.minLen) {...}`（`maxLen / minSent / maxSent / minLong` 同）。
  用 `&&` 判真值，**当值为 `0` 时被当作「空条件」静默跳过**：
  - 用户填「字数 ≥ 0」「句数 ≥ 0」「最长句 ≥ 0」→ 条件失效；
  - 分面点击写入 `minZe=0`（`0–25%` 桶）同理。
- **新行为**：统一为显式判空 + 数值化：
  `if (c.minLen !== undefined && c.minLen !== '' && m.han_len < Number(c.minLen)) { return false; }`
  （`maxLen / minSent / maxSent / minLong` 五处一致，与既有 `minZe/maxZe` 写法对齐。）
- **修复理由**：`0` 是合法边界值，不能被当成「未填」。与 `minZe/maxZe` 的现有写法统一。

- **连带**：`condText()` 回显（原第 263–264、267 行 → 现 `condText` 内）同步改为显式判空：
  新增局部 `has(v)`，`字数∈[..]/句数∈[..]/最长句≥..` 在值为 `0` 时**如实显示**
  （如 `字数∈[0,∞]`）。非零输入的输出文本格式**保持原样**。

## 3. `parse.js` — 离线排序缺 `pid` 兜底（F3）

- **位置**：`searchOffline()`，原第 203–204 行 → 现第 203–210 行。
- **原行为**：`const cmp = cmpFor(cond.sort); if (cmp) { hits.sort(cmp); }`
  只比指标；指标并列时顺序依赖 `rows` 原序。
- **新行为**：在指标比较后追加 **pid 升序兜底**：
  `hits.sort((a,b) => cmp(a,b) || (a.row[0] < b.row[0] ? -1 : a.row[0] > b.row[0] ? 1 : 0));`
- **修复理由**：在线 `web/serve.py` 的 `SORTS` 每一项都是 `metric DESC/ASC, p.pid`
  （`p.pid` 是文本主键，`ORDER BY p.pid` 走**字典序**）。离线补齐同一条 tie-break，
  使「同指标值」的排序结果与在线逐条一致。

## 4. `parse.js` — 声律模式非法字符被当通配符（F8）

- **位置 A**：`pzTest()`，原第 94–102 行 → 现第 94–112 行。
  - **原行为**：`body += (c === '平' || c === '仄') ? c : '.';`
    **任何**非「平/仄」字符（含 `a b c`、数字、标点）都被静默改成 `.`（通配符）→
    `平仄abc` 被当成 `平仄???` 照常检索，用户打错却拿到「看起来正常」的结果。
  - **新行为**：新增白名单 `const PZ_OK = /^[平仄?？]+$/;`；`pzTest` 先 `trim()`，
    只要整串含白名单外字符就 **返回 `null`（非法输入）**，不再静默当通配符。
- **位置 B**：`matchCond()` 的 `if (c.pz)` 分支（原第 144–149 行 → 现 `matchCond` 内）。
  - **新行为**：`const re = pzTest(c.pz); if (!re) { return false; }` —— 非法模式**显式不命中**，
    不会因 `null.test` 抛异常导致页面白屏。
- **位置 C**：`condText()` 中 `声律模式=...` 回显附注 `（含非法字符）`。
- **位置 D**：`parse.js` 导出对象新增 `PZ_OK`；`core/index.mjs` 同步转出，供视图复用（单一真源）。
- **修复理由**：对齐 `web/serve.py:_pz_glob`（第 158–175 行，外部审查 P1-34）与
  `solve/retrieve.py` 的 `PZ_RE`——只允许 `平仄?？`，非法字符显式报错，不静默降级。
  前端选取「返回 null / 不命中」而非抛异常，保证页面不崩。

## 附：未改动、但需主控知悉的一处（不属本轮 8 项，未改）

- `ParseView.vue` 的 `readCond()`（第 86 行）把 `sort` 与 `size` 一并排除出条件，
  随后 `run()` 调用 `api.search(c, page, size)` 时 **`sort` 并未随条件送出**，
  `p.searchOffline(pack.rows, c)` 的 `c.sort` 也恒为 `undefined`。
  即：**「排序」下拉框在在线/离线两条路径都不生效**（服务端恒用默认 `ORDER BY p.pid`）。
  本轮仅按 F3 修好了 `searchOffline` 的 tie-break 契约，**未改动 `sort` 的传递**（超出 8 项范围、
  会改变在线 SQL 的 `ORDER BY` 展示），留给主控决定是否单独修复。
